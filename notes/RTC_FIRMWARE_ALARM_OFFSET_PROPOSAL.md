# Proposed firmware-level RTC alarm-offset faults — 2026-10-07

**Status: approved by the user on 2026-10-07. This dated registration precedes any offset build or simulator run.** This is a separate quality arm. It does not modify the legal LSI schedule, frozen generated or upstream test sources, original ELFs, forecasts, or raw RTC records.

## Motivation and semantics

The scored 64-kHz and 10-kHz faults change the entire RTC calendar rate. An alarm can still fire at the programmed RTC calendar value, even though it arrives early or late by an independent host clock. Their kill rates therefore do not tell us whether a test detects an alarm compare programmed to the wrong RTC calendar second. At nominal 32-kHz LSI, use two separate Zephyr STM32 RTC driver variants that change only the alarm value written by `rtc_stm32_alarm_set_time`: one RTC second before, or one RTC second after, the test-requested target. Keep the RTC calendar, LSI, CPU, SysTick, and simulator settings nominal. This is a deliberately faulty firmware variant, not a legal timing perturbation; rebuilt mutant ELFs are separately hashed and never called frozen-binary RQ2 runs.

Implement a local copy of the requested `rtc_time`, normalize the plus/minus one-second offset across minute/hour/day/month/year boundaries, and pass the copy to the driver's alarm-programming helper. Do not mutate the caller's structure, API mask, callback path, calendar read path, or unrelated driver behavior. Verify that a read-back of the programmed alarm and a calendar read at firing show the expected one-second offset. Store exact driver diff and hashes. If board alarm field masks or rollover behavior prevent a well-defined offset, stop and report the operator invalid.

## Activation and scoring gate

At nominal settings, all three reference tests must pass. Each new offset variant must cause an explicit programmed-alarm readback assertion failure in both alarm references, with a UART line recording requested and programmed RTC calendar values and the signed offset. The counting reference must pass without an alarm-offset activation line. If any reference fails to give this pattern, do not score broad suites; keep the activation record and diagnose. The readback assertion checks the offset independently of the oscillator; event assertions remain in each reference.

Run each of the two activated variants once against all 69 existing eligible suites, with new exclusive result files and preserved source/ELF/platform/driver/trace hashes. The alarm mutation is applicable to **41 alarm suites**: 39 LLM-generated callback/pending suites and two upstream (human) alarm cases. The remaining **28 calendar-counting suites** (27 LLM-generated and one upstream (human)) do not set alarms. Run them as non-activation controls as requested, but report their outcomes separately as **not applicable** to alarm-offset kill rates. **Preregistered kill rule:** count a kill only when UART shows the signed offset activated and the selected ztest case explicitly fails. An explicit selected-case pass is a survivor. No activation is inactive and unscored; startup/monitor errors or ambiguous cases remain missing. Report per-task and model × prompt results beside, but never pooled with, the existing 64-kHz/10-kHz oscillator and nonarrival scores. Replay explicit kills from the same ELF and platform; compare selected-case verdict, error, and offset log. Preserve original records and unknowns.

This 41/28 split is a methodological limit of an alarm-only fault. A calendar-counting-specific firmware fault would require its own separately registered operator and reference activation before counting tests could have a meaningful kill denominator.

## Estimated cost and review gate

Two variants × 69 suites require 138 suite runs, plus four alarm-reference activation runs and two counting-reference non-activation controls; include nominal reference controls. The previous two-fault arm used 2.10 summed simulator wall hours for 138 records (median 47.7 s per run). Rebuilding two variants adds roughly 138 × 12.3 s, or 0.47 summed hours, based on the earlier median build time. Three disjoint workers give an ideal execution floor below one hour; allow **1.5–3 hours wall time after implementation** for builds, simulator contention, activation, replay, and audit, plus roughly **1–2 hours engineering** for a date-safe driver offset and validated registration. These are estimates, not promised runtime. The user approved the experiment on 2026-10-07.
